# Reach: Streaming Single-Source Reachability — Incremental Alpha vs clingo

The *reach* benchmark now uses the **exact reachability program and graph grid
from the original Alpha paper** — Leutgeb & Weinzierl, *"Techniques for
Efficient Lazy-Grounding ASP Solving"* (DECLARE 2017 / LNAI 10997, 2018),
Sect. 5, "Reachability", Table 5 — but drives it in a **streaming** setting:
the graph grows one edge-chunk at a time and the session re-solves each shot.

The paper runs this program single-shot and finds clingo the fastest (it is a
pure positive program with no grounding bottleneck and no search). Our
contribution is orthogonal: in the **streaming** regime, where each new edge
extends the graph, incremental Alpha keeps its grounder + solver state alive and
pays only for the delta, while any batch solver — clingo included — re-grounds
the whole cumulative graph every shot. The per-shot ratio then compounds over
the length of the stream.

Where [cutedge](../cutedge/README.md) demonstrates **lazy grounding's structural
advantage on choice × recursion**, reach demonstrates **incremental Alpha's
grounder-state-retention advantage on streaming Datalog queries**.

## The encoding

The paper's reachability task, verbatim: *"a simple positive program computing
reachability in a large graph. The task is: given some start vertex of a graph,
compute the set of all vertices reachable from the start vertex."* Positive,
no negation → exactly one answer set (the reachable set):

```prolog
reachable(V) :- start(V).
reachable(V) :- reachable(U), edge(U, V).
start(1).
```

This is the **single-source, unary** closure (`reachable/1`) — it materialises
the forward-reachable *set* from a fixed start vertex, O(V) atoms. That is
deliberately lighter than the earlier binary transitive-closure-plus-query
variant (kept as `encoding-tc-query.lp`, which materialises O(V·|TC|) and was
built to punish eager re-grounding). Using the paper's program keeps this
benchmark directly comparable to the published Alpha results, and its lighter
closure lets the stream scale to the paper's largest graphs (10 000 vertices,
80 000 edges) without the density cliff the binary variant hits past ~10 000
edges.

## The graphs

Random directed graphs at the paper's exact grid (Table 5, written as
*vertices / edge-multiple*): 1 000 and 10 000 vertices, 4 000–80 000 edges,
*"edges between two randomly selected nodes, i.e., no further structure."*

| paper label | vertices | edges | file |
| ----------- | -------: | ----: | ---- |
| 1000/4  | 1 000  | 4 000  | `edges-rand-v1000-e4000.lp` |
| 1000/8  | 1 000  | 8 000  | `edges-rand-v1000-e8000.lp` |
| 10000/2 | 10 000 | 20 000 | `edges-rand-v10000-e20000.lp` |
| 10000/4 | 10 000 | 40 000 | `edges-rand-v10000-e40000.lp` |
| 10000/8 | 10 000 | 80 000 | `edges-rand-v10000-e80000.lp` |

Generated by `gen-random-graph.py` (deterministic given `--seed`): distinct
directed pairs, no self-loops, emitted in random arrival order so the streaming
driver adds them in a natural order. The first emitted edge always leaves the
start vertex (1), so the reachable set is non-trivial (e.g. 982/1000 reachable
in `edges-rand-v1000-e4000.lp`, seed 0). The paper uses 10 random instances per
size; regenerate the whole grid — or 10 seeds each — with:

```sh
python3 gen-random-graph.py --grid                 # 1 instance per size (seed 0)
python3 gen-random-graph.py --grid --instances 10  # 10 seeds per size
```

## Relationship to the paper's Table 5

The paper's Table 5 (single-shot batch, average of 10 instances) has **clingo
fastest** — 0.11–2.27 s vs Alpha's 2–16 s — precisely because the program has no
grounding bottleneck and no search, and *"the optimizations for solving purely
positive programs in Clingo make it the fastest here."* Among the lazy-grounding
solvers Alpha is the fastest on the large instances.

That single-shot result is unchanged and not what this benchmark contests. The
streaming numbers below are a *different experiment on the same program*: they
measure the cost of keeping an evolving graph's answer live as edges arrive, and
there incremental state retention beats rebuild-from-scratch — for clingo and for
batch Alpha alike.

## Headline: the four-way sweep

`bench-reach-sweep.sh` streams **each** grid instance into an initially-empty
graph over 25 shots and totals four solvers on that same per-instance stream —
every shot adds only `edge/2` facts (vertices are implicit edge endpoints, never
their own facts).

| instance | edges | inc Alpha | batch Alpha | clingo | clingo MSS | paper Alpha | paper clingo |
| -------- | ----: | --------: | ----------: | -----: | ---------: | ----------: | -----------: |
| 1000/4  |  4 000 | **0.18 s** | 0.65 s |  0.91 s | 54.8 s | 2.13 s | 0.11 s |
| 1000/8  |  8 000 | **0.25 s** | 1.12 s |  1.16 s | 26.0 s | 3.19 s | 0.21 s |
| 10000/2 | 20 000 | **0.55 s** | 1.79 s |  1.72 s | **FAIL** | 10.95 s | 0.52 s |
| 10000/4 | 40 000 | **1.17 s** | 5.28 s |  2.82 s | **FAIL** | 13.06 s | 1.09 s |
| 10000/8 | 80 000 | **2.32 s** | 14.25 s | 4.86 s | **FAIL** | 16.62 s | 2.27 s |

(Apple Silicon laptop, clingo 5.8.0, OpenJDK 17, seed 0, 25 shots/instance.)
Incremental Alpha wins every instance: **2.1–5.1× over rebuilt clingo, 3.2–6.1×
over batch Alpha**. The four left columns are the same per-instance stream; the
two right columns are the paper's single-shot Table-5 solves (independent
instances, 2018 cluster — reference only).

The four modes:

- **inc Alpha** — one live `AlphaSession`, solver + grounder state retained across shots.
- **batch Alpha** — session rebuilt from scratch each shot (same JVM).
- **clingo** — clingo re-invoked from scratch each shot.
- **clingo MSS** — clingo multi-shot: one long-lived `Control`, every edge a ground
  `#external edge(a,b)`, recursion grounded once over `#external edge(X,Y):node(X),node(Y)`.

**What the MSS column shows.** At V = 1000 the external universe is 10⁶ atoms:
MSS runs, but every solve drags that whole program, so it is **100–300× slower**
than lazy Alpha (tens of seconds). At V = 10 000 the universe would be **10⁸**
edge externals — the cutedge/groundexp grounding wall — and MSS is not viable at
all (`clingo-multishot.py` bails above a 4 M-external cap). This is the crux:
streaming reachability wants *lazy* grounding. Alpha discovers new node ids
straight from the edges it is given; MSS must pre-declare the node universe and
pay V² for it, whether or not those edges ever appear.

**The single-shot verdict reverses under streaming.** In the paper's batch
Table 5, clingo beats Alpha on every row (positive program, no grounding
bottleneck, no search). Stream the same program and incremental Alpha beats
*rebuilt* clingo on every instance — retaining grounder + solver state across
shots is what flips it.

### Incremental stays flat as the stream lengthens

Splitting one instance into more shots leaves incremental Alpha almost unchanged
while every rebuild baseline grows ~linearly (each shot re-grounds the whole
cumulative graph). On 1000/8:

| shots | edges/shot | inc Alpha | clingo (rebuilt) | batch Alpha | clingo speedup |
| ----: | ---------: | --------: | ---------------: | ----------: | -------------: |
|    10 |        800 | 0.30 s | 0.55 s |  5.87 s | 1.86× |
|    25 |        320 | 0.30 s | 1.21 s | 12.02 s | 3.99× |
|    50 |        160 | 0.34 s | 2.60 s | 23.55 s | 7.66× |

The longer the stream, the bigger the win — the per-shot work ratio is amplified
by the number of shots. (At very few shots, e.g. 5, clingo re-grounds too rarely
for the gap to open, so the sweep above uses 25.)

## Per-shot pattern

`edges-rand-v1000-e8000.lp` streamed in 25 shots of 320 edges, `live` mode:

| shot | edges total | incremental Alpha |
| ---: | ----------: | ----------------: |
|    1 |         320 |            0.025 s |
|    5 |        1600 |            0.032 s |
|   10 |        3200 |            0.010 s |
|   15 |        4800 |            0.007 s |
|   20 |        6400 |            0.009 s |
|   25 |        8000 |            0.008 s |
|      |   **total** |          **0.253 s** |

Incremental Alpha shows a small early bump (shot 1 pays first-solve setup; the
closure expands fastest while the reachable set is still growing) and then
quiesces to a few milliseconds per shot as later edges only trigger small local
joins. Every rebuild baseline instead grows monotonically with cumulative edges.

## Why "incremental clingo" doesn't help here

This is the `clingo MSS` column above, driven by `clingo-multishot.py`. clingo's
multi-shot Python API requires declaring the edge relation as `#external` over the
node universe (which grounds the recursive rule over that universe upfront —
O(V²) here), because re-adding the encoding in a subprogram is rejected due to
atom-ID re-declaration. Neither gives clingo what `AlphaSession` gives Alpha for
free: a grounder that accepts new facts *and new node ids* without re-grounding
existing rules, and a solver that resumes from dl = 0 with its working memory
intact. So MSS is 100–300× slower where it runs (V = 1000) and not viable at all
where the node universe is large (V = 10 000 → 10⁸ externals). Rebuilt-each-shot
is the workable clingo baseline; MSS is included to show the multi-shot failure
mode directly.

## What state retention does on this benchmark

`AlphaSessionImpl` takes its *live-solver* path (see
[cutedge/README](../cutedge/README.md#what-state-retention-actually-does-today)).
For reach specifically:

- `NaiveGrounder.extendWithFacts` puts the new edges in the `edge` working memory
  and marks them recently-added.
- The `edge`-starting variant of the recursive rule
  `reachable(V) :- reachable(U), edge(U, V)` fires on each new edge, joining it
  with the cumulative `reachable/1` working memory through its position-indexed
  lookup. Each new edge triggers exactly the joins it participates in,
  irrespective of how many reachable atoms have accumulated.
- The cumulative `NoGoodStore`, atom store, and (degenerate, here) VSIDS activity
  carry over. The solver resets to decision level 0 and resumes.

The `selectiveWakeUpForNewFacts` optimisation in
[`NaiveGrounder.java`](../../alpha-core/src/main/java/at/ac/tuwien/kr/alpha/core/grounder/NaiveGrounder.java)
is what makes this cheap: when every new-fact predicate in a rule body is itself
a starting literal of that rule (here `edge`), new facts already retrigger the
rule via their own `FirstBindingAtom`, so re-marking the other body predicate's
instances (`reachable`) would redo the same joins. Skipping that redundant
wake-up is what keeps per-shot cost proportional to the edge delta rather than to
the cumulative reachable set.

## Methodology and caveats

**What's measured.** Wall-clock per `solve()` call (Java side, `System.nanoTime`)
and per clingo / batch-Alpha invocation (shell, `time.time()`).

**Honest fairness notes:**
- **JVM startup.** Incremental Alpha's column excludes JVM startup (one JVM
  across all shots). The clingo and batch-Alpha columns include process startup
  per shot. Startup is a small constant; the growing gap is grounding, not
  startup — subtracting ~40 ms/shot from clingo's 50-shot total (2.60 s) still
  leaves ~0.6 s vs incremental's 0.34 s.
- **The paper's single-shot verdict stands.** On one big batch solve of this
  program clingo wins (Table 5). This benchmark only claims the streaming regime.
- **Memory.** Not measured. Incremental Alpha's grounder state accumulates the
  full `reachable/1` working memory plus the edge relation for the lifetime of
  the stream.

## How to reproduce

```sh
./gradlew :alpha-cli-app:installDist                                   # one-time
python3 examples/reach/gen-random-graph.py --grid                      # one-time (writes the 5 grid instances)

# four-way sweep across the whole grid (the headline table):
SHOTS=25 examples/reach/bench-reach-sweep.sh
SHOTS=25 examples/reach/bench-reach-sweep.sh edges-rand-v1000-e8000.lp  # single instance, still 4-way

# single-instance per-shot detail (3-way live vs clingo vs batch Alpha):
SHOTS=50 examples/reach/bench-incremental.sh edges-rand-v1000-e8000.lp
```

Standalone Java driver (no clingo / batch comparison), using absolute paths
(the gradle task runs from the module directory):

```sh
R=$(pwd)
./gradlew :alpha-cli-app:runIncrementalReachBenchmark \
    --args="$R/examples/reach/encoding.lp $R/examples/reach/instances/edges-rand-v1000-e8000.lp 25 live"
```

The fourth argument is the mode: `live` (one answer set per shot, live-solver
path — the headline incremental result), `rebuild` (drain the iterator each
shot), or `batch` (destroy and rebuild the session each shot; same-JVM baseline).
